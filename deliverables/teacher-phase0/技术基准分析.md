## ② DeepSeek Harness 深析与 butler 映射验证

### 2.1 Harness 架构要点（证据：docs）

- **一切皆插件**：`docs/architecture.zh.md` L11-13——"插件向共享上下文贡献服务、类型化事件和可逆的副作用……不存在需要打补丁的特权内核"；产品每一部分（模型适配器、工具注册表、会话日志、agent loop 本身）都是插件，可从配置替换。
- **核心包表**（architecture.zh.md L45-51）：`core/session`（仅追加 SessionEvent 日志，`ctx.sessions`）、`core/tools`（"作用域化的工具注册表和带把关的执行流水线"，`ctx.tools`）、`core/agent`（Agent 接口 + `agent/*` 事件）、`core/agent-loop`（默认驱动器，`ctx.agentLoop`）、`core/scope`（按 agent 划分作用域）、`llm/llm`（"消息与流式词汇表，以及适配器 seam"，`ctx.llm`）。
- **轮次流程**（architecture.zh.md L71-86）：`turn/start → 领取输入 → 组装 prompt+工具 schema → agent/pre-step（可拒绝/改写） → step/start → agent/request → llm/stream → tool/call* → tools/pre-execute → tools/execute → tools/post-execute → tool/result* → step/end →（工具欠一个请求则领取下一步）→ turn/end`。一个**轮次**含零或多个**步骤**（步骤=一次模型请求+它调用的工具）；`tools/*`、`agent/*` 是 waterfall 事件（监听器必须 `next()` 委托）。
- **事件三域**（architecture.zh.md L57-63）：会话事件（持久事实，重载后仍在）、Agent 事件（观察/拦截进行中工作）、能力事件（向 seam 附加策略/适配器）；"事件就是扩展点"。
- **工具流水线顺序**（docs/tool-execution-pipeline.zh.md L8）："tools/pre-execute waterfall 首先运行，随后是单调守卫，然后运行 tools/execute 和 tools/post-execute waterfall；这三个 waterfall 可以改写一次调用"，其后是定义自有的 `finalizeContent` 与同步的 `tools/result`（冻结的权威结果）。pre-execute 可 `allow/deny/ask`（ask → `ctx.approval` 一次性审批，缺失/未答一律拒绝，tool-execution-pipeline.zh.md L18、L40-42）。
- **单调守卫**（docs/subsystems/tools.zh.md L313-324）：`ToolGuard` 返回类型**不含 allow**——守卫只能缩减权限，"后续监听器无法把拒绝变回允许"。
- **审批 fail-closed**（docs/subsystems/approval.zh.md L21-28）：`ApprovalOutcome` 是闭合枚举 `allowed-once|rejected|cancelled|unavailable`，"缺失、不负责、抛异常或不合规的应答者产生 unavailable，而非放行"。
- **防御性模式**（docs/defensive-patterns.zh.md）：正交结果独立上报（L9，timedOut/signal/exitCode 各自独立，勿嵌套）；公共约定两侧都要遵守/入 API 前规范化（L13）；分发器中隔离回调异常（L27）；**绝不将环境变量或可预测路径暴露给不可信输出**（L31，清理 `*KEY*/*SECRET*/*TOKEN*/*PASSWORD*` 环境变量）。
- **模型扩展点**（architecture.zh.md L116）：添加模型提供方 = "在 ctx.llm 上注册其适配器"。

### 2.3 差距与取舍（butler 相对 harness 的有意简化）

以下差距均为**有意简化**（设计规格驱动），逐条给出取舍理由，供后续演进决策时对照：

1. **静态注册 vs 插件热插拔**。Harness：一切皆插件，注册是可逆副作用（Cordis disposer），支持作用域遮蔽/限制交集/运行时卸载（tools.zh.md L496-525 的 register/restrict/guard 均返回精确 disposer；scope.zh.md 的 ScopedLayers 层叠）。我方：`ToolRegistry` 是进程内普通 dict，由 `build_m2_registry()` 工厂在启动时显式组合 9 本地 + 7 远程共 16 工具（registry.py L129-143），docstring 明言"不使用 eval/getattr 动态反射"。**取舍**：教师端工具集变化频率低，静态注册换来类型化 I/O 强校验与审计简单；代价是新增/下线工具需改代码重启，无运行时扩展与 per-agent 作用域。若未来出现"按学校/按班级差异化工具集"需求，再引入 harness 的 scope layer 思想。
2. **单遍管线 vs 多步循环**。Harness：turn 内 0..n 步循环——工具结果欠新请求则继续 claim 下一步（architecture.zh.md L83），支持 steering 中途引导、inbox 注入、pre-step 拒绝重入（agent-lifecycle.zh.md 时序图）。我方：一次 run 只走一遍 Context→Plan→Policy→Execute→Compose，模型请求 ≤ `UsageLimits(request_limit)`（runtime.py L311-320），工具 ≤5（policy.py 步骤5），Compose 确定性组装、不再回模型。**取舍**：延迟/成本上界固定、审计链（AgentRun/AgentStep/ToolInvocation）与判分等强一致场景更简单；代价是"工具结果需要模型二次推理"的任务（如多轮纠错式解题辅导）表达不了，需要时应在 Execute 后增加受预算约束的受限回流步骤，而非推翻管线。
3. **每请求重建 vs 进程常驻**。Harness：agent 是进程常驻对象，带 inbox/status/续跑（architecture.zh.md L104-109 seam、agent-lifecycle）。我方：`ButlerRuntime` 按请求组装（`build_shadow_runtime()` 每次新建，runtime.py L423-434），模型请求计数用 ContextVar 而非实例属性（model_adapter.py L39-41："同一 Runtime/Adapter 连续/并发 run 不累计、不串扰，禁止共享整数方案"）。**取舍**：无共享可变状态 → 并发安全天然成立；代价是每请求重复查注册表/装配 prompt（在 16 工具规模下可忽略），且没有跨请求记忆（会话态由 state.py + DB 承担）。
4. **确定性 PolicyGate vs 交互式审批**。Harness：`ctx.approval` 一次性人审（allowed-once）+ ask/never 会话策略 + 审计事件对（approval.zh.md）。我方：PolicyGate 全确定性（角色/场景/风险/预算/范围），无人在环审批，管理员开关走 `system_configs["butler.authorization"]`（runtime.py L119-131）。**取舍**：学生端场景无法要求教师实时审批，确定性拒绝 + 脱敏账本即可满足合规；代价是"低风险但需临时授权"的操作无法放行——若教师端出现此类操作，可引入 harness 的 allowed-once 审批事件对（approval/asked + decided 的持久审计配对思想）。
5. **关系账本 vs 追加事件日志**。Harness：SessionEvent 仅追加日志是模型上下文唯一来源，"模型可见即已记录"，可回放重建（architecture.zh.md L96-100）。我方：AgentRun/AgentStep/ToolInvocation 关系表 + 脱敏 digest（runtime.py L86-97、L192-243；账本"只存脱敏摘要，不存密钥/完整文本/思维链"，docstring L10）。**取舍**：关系账本可 SQL 查询、易做运营报表与合规审计；代价是失去"从日志重建模型上下文"的能力（我方每请求重新组装上下文，context.py）。这是数据合规（不落思维链/原文）下的正确取舍，不要为对齐 harness 而回退。
6. **异常处理粒度**。Harness 防御性模式要求"正交结果独立上报"（defensive-patterns.zh.md L9：timedOut 与 exitCode 各自独立上报）。我方 ToolResult 有独立 `ok/error_code/retryable/degraded/latency_ms/execution_status` 字段（contracts.py L110 起），基本符合；但 orchestrator/llm 层大量 `except Exception: logger.info(...)` 吞异常（orchestrator.py L63-66、llm.py L87-89）只留截断日志，缺少 harness 式的"结构化失败上报"。**建议**：在 ai_calls/learning_events 账本上补 `degraded_reason` 正交字段，而非只吞日志——这是从 harness 防御性模式可低成本摘取的一课。
