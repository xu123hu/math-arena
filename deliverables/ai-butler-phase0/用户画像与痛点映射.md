# 用户画像与痛点映射 · AI 管家悬浮球 + 后台任务中心

> 日期：2026-09-01 ｜ 画像证据全部来自既有实测文档与竞品调研（不新造），学生画像卡为本轮补全（此前缺口）。

## 一、画像卡（3 张）

### 画像 S1 · 学生 · 高三中等生「备考多线并行型」（本轮补全）

- **基本属性**：高三，数学 90~120 分（平台目标用户），PC/平板为主，晚间自习+周末整段、课间碎片时间。
- **使用场景**：晚自习先刷一套限时练 → 错题进错题本 → 有不会的拍照问 AI；睡前在手机上想「明天练什么」。**多线并行**：练题、订正、复习、看课互相打断。
- **第一分钟想干什么**：打开就知道「现在该练什么、练到哪了」；提交一件事（出题/订正/上课）后能去干别的，**回来时结果已经等着他**。
- **最怕什么**（证据原话）：
  - 「永远转圈的『AI 生成中』、永远加载失败的面板」（体验缺陷清单 P0 系列）；
  - 「求解耗时长」（引导解题开场 22.3s，学生端场景清单实测）；
  - 「网络中断后学生仍会以为已保存，回到课堂后才发现位置或笔记丢失」（student-ai-upgrade-assessment §7.2）；
  - 竞品差评印证：「题总是扫错……天天让我充 VIP」（小猿AI）、「ai 会漏题 漏答案」（作业帮）——AI 不可信。
- **现有替代方案**：纸质练习册+答案册、同学互助、K12 竞品 App（均有 VIP 墙）。
- **对 AI 管家的期望与顾虑**：期望=「我说一句话它就把题出了/把课备了」；顾虑=AI 出的题超纲/答案错（被坑时间），管家打扰刷题（应试生反感弹窗——管家人格设计四红线既有结论）。

### 画像 T1 · 教师 · 王老师「批改减负型」（复用 teacher-phase0，扩展后台任务视角）

- **基本属性**：38 岁，县城高中，2 个班约 110 人；晚自习办公室 PC 批改 2~3 小时/天，手机看通知。
- **第一分钟**：「看到今天要批多少份、哪些学生/哪些题需要关注」。
- **最怕**：AI 批改不可信（错批要重批）、误点丢数据；**「对『假数据、点了没反应、AI 内容不可信』零容忍」**（教师端优化提示词 §0 原话）。
- **后台任务视角扩展**：批改/学情报告/分层作业生成都是「批量大活」——他需要**提交后离开、手机上收到完成通知、随时回来接着批**，而不是守着进度条。教师端诊断原话：「『生成PPT』无响应……按钮形同虚设」「老师无法判断是处理中还是已经完成」。

### 画像 T2 · 教师 · 李老师「出题质量焦虑型」（复用 teacher-phase0，扩展管家视角）

- **基本属性**：26 岁新教师，1 班 45 人；晚间备课出题 20~40 分钟。
- **第一分钟**：「按课题出一套可信的练习，最好直接能布置」。
- **最怕**：题目模板重复、超纲、答案错误被学生问倒。
- **管家视角扩展**：理想动作链=「跟管家说：给我出圆锥曲线 30 分钟练习」→ 管家走练题中心同一套出题内核（不另起炉灶）→ 生成完通知 → 一键预览→布置。这正对应用户命题第一例；竞品侧「AI 出题不是壁垒，题-教学意图对齐才是」（teacher-phase0 竞品调研结论）——管家必须复用五闸质检，不许绕过。

## 二、痛点 → 功能映射（含解决程度目标）

| # | 痛点（证据） | 对应功能 | 解决到什么程度（验收口径） |
|---|---|---|---|
| P1 | 出题/生成必须守着页面（练题同步出题 student_router.py:1052；课堂/课程生成虽有 create_task 但入口深、无通知） | 通用任务中心：所有生成类操作落任务行，离开页面继续跑 | 任务行有 status/progress；关浏览器后任务仍到终态；重新打开可见结果（curl+SQL 证据） |
| P2 | 完成了没人告诉我（全部拉取式轮询，无通知；butler actions 仅学生端拉取） | 完成通知：站内红点 + 任务中心角标 + 悬浮球气泡；「仅在值得时通知」+ 反骚扰限额 | 终态任务产生通知；同任务不重复推；学生端每日主动推 ≤3（沿用 butler 纪律） |
| P3 | 生成结果散落各业务页，失败静默消失（D5 pending_review 无异步收尾；失败课堂从最近课堂排除） | 历史即资产：任务中心列表（含失败）+ 失败可重跑 + 产物自动落对应业务模块（题目→练题/错题，课堂→历史课堂） | 失败任务可见可重试；成功产物在业务模块可找到（走查证据） |
| P4 | 想要「说一句话就办成事」（学生：出题/上课/解题；教师：备课/组卷/报告） | AI 管家悬浮球（双端）：对话 → Planner 出 ActionPlan → 受控调用领域工具 | 三条演示链路端到端走通：出题、双师课堂、解题转接（含图片） |
| P5 | AI 代操作不可信（竞品差评：「AI 漏答案」「编造文献」；教师「错批要重批」） | 沿用 Butler v2 纪律：PolicyGate 风险分级 + 工具白名单 + 幂等键 + agent_runs 全记账 + 产物可追溯（哪次 run 生成的） | 每个管家产物可回查 run/工具调用记录（SQL 证据） |
| P6 | 断线丢进度（DualView 静默吞写失败；agent chat 断连生成中断） | 任务化执行与连接解耦（classroom 范式推广）；断线不中断生成；进度可恢复 | 断开 SSE 后任务继续至终态；重连/重开页面见完整结果 |
| P7 | 长耗时无过程可见（22.3s 开场、无加载状态 B-03） | 任务进度（progress/阶段文案）+ 悬浮球运行中状态 | 任务行/悬浮球显示阶段进度；失败显示原因+重试按钮（禁永久转圈——既有纪律） |

## 三、砍单清单（本期不做 + 理由）

| 不做 | 理由 |
|---|---|
| Celery/独立 worker 进程 | 与 M1 决策一致（workers/__init__.py 注释）；单进程 asyncio + DB 状态 + auto-resume 已够当前量级；基准 Dify 的多队列复杂度不适用于我们 |
| 浏览器 Web Push / 短信 / 邮件通知 | 通知通道一期站内即可闭环（网站在线时红点+气泡可见）；Web Push 需 HTTPS+Service Worker 基建，挂不到本期限链路卡；沿用砍「家校 IM 自建」纪律 |
| 定时任务（automations，如每日晨练） | 有价值但非本命题主链路（用户没提周期性）；Open WebUI 模型已存档，二期做 |
| 学生端 v2 管家全量场景迁移 | 一期只登记 student.chat + 3 个工具；其余 9 个本地工具渐进迁移（teacher 端 19 工具经验） |
| 管家语音输入/新人格形象 | 「小婷」人格与红线已定（product-strategy §4.7），不推翻；语音与命题无关 |
| 移动端/小程序适配 | 平台是 Web；悬浮球只做桌面 Web 形态 |
| 跨 App 全局快捷键 | Notion/豆包是桌面 App 才有；我们是 Web，⌘K 唤起（教师端已有）已覆盖 |

## 四、画像—链路预连接（供阶段 1 展开，不做断头路）

- S1：练题页出题慢 → 悬浮球说「出 30 分钟圆锥曲线」→ 后台任务 → 继续刷旧题 → 通知 → 点开进入练习（产物自动入练题中心与历史）。
- T2：备课页说「按今天课题出一套练习」→ 任务中心可见进度 → 通知 → 预览→布置（产物入教师备课/作业链路）。
- S1：错题本拍照不会做 → 悬浮球转引导式解题（带图）→ 后台解题 → 通知 → 会话沉淀在对话历史。
- T1：批改页说「生成这次作业的讲评报告」→ 后台跑 → 通知 → 讲评材料挂到课堂会话。

> 每条链路均落在「既有内核 + 新任务表 + 通知」上，不新增独立业务内核；链路卡全集属阶段 1 交付。
